1. Introduction

This document covers the execution of transactions without conflicts and with concurrency for maximum speed.

A transaction consists of:

  1. Reading data
  2. Performing calculations
  3. Writing back results

Note: The calculations themselves are not the database's concern.

2. Write Operations

Type Description
Normal Write A read operation has been performed before it
Blind Write No read performed before it (e.g., overwriting)

3. ACID Properties

A correct set of transactions follows the ACID properties:

3.1. Atomicity

  • Transactions must either fully execute or have no effect
  • Requires recovery mechanisms

3.2. Consistency

  • Transactions must start from a consistent state and commit with a consistent state
  • What constitutes "consistent" is defined by business rules
  • Affected by both recovery and concurrency control:
    • Poor recovery from abortions can cause inconsistency
    • Poor concurrency management can cause inconsistency

3.3. Isolation

  • Ensures that the effect of transactions is equivalent to running them serially, even when executed concurrently
  • Ensured by maintaining serializability

3.4. Durability

  • Committed transaction effects must persist under all conditions
  • Can be ensured by making data backups

4. Schedule Requirements

We want schedules to be:

  • Serializable
  • Recoverable (specifically, cascadeless recoverable)

5. Recovery

5.1. Overview

  • Atomicity requires a recovery management component
  • Recovery systems use: undo, redo, rollback, aborting, and committing operations
  • Requires transaction logs
  • Atomicity depends on recoverability

Important: Recovery here refers to recovering from the effects of an aborted transaction, not "Durability" recovery.

5.2. Recoverability Conflicts

Recoverability is affected by two conflicts:

  • WR (Write-Read) conflicts
  • WW (Write-Write) conflicts

Note: RWR (Read-Write-Read) conflict doesn't affect recoverability; it affects serializability/isolation.

5.3. Types of Recoverable Schedules

5.3.1. Cascading Recoverable Schedules

Condition: If transaction T2 reads data written by transaction T1, then T1 must commit before T2.

  • If this condition is not satisfied, irrecoverability occurs
  • When satisfied, we have a cascading recoverable schedule
  • Removes the WR conflict
  • However, cascading recovery can be costly (multiple transactions may need to abort)

5.3.2. Strict Recoverable Schedules

Conditions: Other transactions cannot read or write data that the current transaction has written to (i.e., no WR or WW conflicts).

Reasoning:

  • In WW conflict cases, the DBMS cannot determine whether to keep the change or not
  • It cannot identify whether data was written by the aborted transaction or another transaction
  • When these conditions are met, we have a strict recoverable schedule
Schedule Type Conflicts Allowed Recovery Cost
Cascading Recoverable WW only High
Strict Recoverable None (no WR, WW) Low

6. Serializability

6.1. Definition

  • A serial schedule has the form: T₁ → T₂ → T₃
  • Concurrent schedules can be "equivalent" to serial schedules
  • A schedule is equivalent to another if:
    • Each read operation in both schedules reads the same value
    • The final write is performed by the same operation in both schedules

6.2. Schedule Types

Schedules
├── Serial (low throughput)
└── Concurrent (high throughput)
    ├── Serializable (equivalent to serial)
    └── Non-serializable

The DBMS deals with concurrent serializable schedules.

6.3. Concurrency Control

  • The concurrency control component prevents non-serializable schedules
  • Ensures serializability and thus isolation
  • Implemented using locks and other techniques
  • Ensures only serial-equivalent schedules execute

6.4. Conflicts in Concurrent Schedules

Note: These are written in the order the conflict occurs (RW means read then write).

In all cases below, the first operation happens, then the second, but the transaction of the first operation is uncommitted or still ongoing.

Conflict Name Description
RWR Unrepeatable Read Read, then Write, then Read again
WR Dirty Read Write, then Read
WW Lost Update Write, then Write

6.4.1. Important Notes About Conflicts

  • These conflicts are NOT present in any serial schedule (each transaction commits before another starts)
  • These MAY be present in a serializable schedule
  • A conflict-equivalent schedule may have these conflicts, but a conflict-serializable schedule doesn't (by definition, it can be transformed into a serial one by commuting non-conflicting operations)
  • These 'conflicts' may not actually be problems—they indicate ways transactions can affect each other and deviate from serial behavior

6.4.2. Examples

Example 1 (WR Conflict): If T1 writes to A and T2 reads A, this may not be problematic if in the serial schedule T1 → T2, the same operation in T2 reads the same value written by T1.

Example 2 (WW Conflict): If three transactions consist of only the operation W(B) and the schedule is equivalent to T1→T2→T3, then the WW conflict between T1 and T2 is not significant as either can write early or late. What matters is that the last update is done by T3.

This is the basis of "view serializability"—the view must be the same.

In conflict serializability: W₁(B) → W₂(B) → W₃(B) is not equivalent to W₂(B) → W₁(B) → W₃(B). In view serializability: They are equivalent.

6.5. Types of Serializable Schedules

6.5.1. View Serializable (VSS)

The more general type of serializable schedule.

Two schedules S1 and S2 are view-equivalent when:

  1. If transaction Tᵢ in S1 reads an initial value for object X, so does the same transaction Tᵢ in S2
  2. If transaction Tᵢ reads a value (for object X) written by transaction Tⱼ in S1, it must do so in S2
  3. If transaction Tᵢ in S1 performs the final write for object X, so does the same transaction Tᵢ in S2

6.5.2. Conflict Serializable (CSS)

A more restrictive type of serializable schedule.

  • When non-conflicting operations can be swapped (commuted) to transform one schedule into another, they are conflict-equivalent
  • If a schedule is conflict-equivalent to a serial schedule, it is CSS
  • Called "conflict equivalent" because the two schedules have the same conflicts
  • Easier to implement than VSS

Note: Here conflicts don't depend on "commit" as they do in recoverability.

Property View Serializable Conflict Serializable
Generality More general More restrictive
WW conflicts considered Can be ignored Must be considered
Implementation complexity Harder Easier

6.5.3. Precedence Graphs

Schedules can be depicted using precedence graphs, where arrows show which transaction must come before another.

The arrow-making process differs based on serializability type:

  • CSS: Arrows formed by WW, WR, RW conflicts
  • VSS: Arrows formed by WR, RW conflicts (WW can be ignored, along with who did the last write)

Note: To be safe, also include the first condition from the view serializability definition.

7. Concurrency Control Protocols

7.1. Lock-Based Protocols

7.1.1. Lock Types

Lock Type Symbol Allows Reading Allows Writing Can Share
Shared Lock S Yes No Yes
Exclusive Lock X Yes Yes No

Implementation Note: These locks are probably implemented using semaphores, though not exactly the same.

  • If a lock is denied, a transaction must wait or be aborted
  • S locks can be granted even if other transactions hold S locks on the same data item
  • X locks cannot be shared

7.1.2. Basic Locking

  • Does not ensure serializability
  • Not recommended for production use

7.1.3. Two-Phase Locking (2PL)

  1. Phases
    Phase Description
    Growing Phase Lock-only acquiring phase
    Shrinking Phase Lock-only releasing phase
  2. Properties
    • Allows serializability (not all serial schedules get executed)
    • If a schedule is allowed using 2PL, it must be CSS
    • The converse need not be true
    • Order of lock points matches order of equivalent CSS serial schedule

    Note: No upgrading or downgrading from S to X. If a write must be performed after a read, take an X lock from the start.

7.1.4. 2PL with Upgrading and Downgrading

  1. Lock Operations
    Operation From To Allowed Phase
    Upgrade S X Growing only
    Downgrade X S Shrinking only
  2. Benefits
    • Can reduce delays and abortions
    • Can execute more CSS schedules
    • Cannot execute non-CSS schedules (upgrading/downgrading doesn't change this)
  3. Problems with Basic 2PL

    Both basic 2PL variants (with or without upgrading/downgrading) suffer from:

    • Irrecoverability → Solved by Strict 2PL
    • Deadlock → Solved by Conservative 2PL
    • Starvation/Delay → No solution available

7.1.5. Strict 2PL

Rule: Transactions must hold all exclusive locks until they commit or abort.

  1. Benefits
    • Prevents dirty reads
    • Schedules will be recoverable and cascadeless
    • Other transactions can access data only after the current transaction commits
    • Shared locks can be released in the shrinking phase before commit

7.1.6. Conservative 2PL

Rule: A transaction must either get all locks before starting or release all and try again later.

Purpose: Fights deadlock by preventing the hold-and-wait condition.

Note: X locks can be released before commit, so it can suffer from:

  • Irrecoverability
  • Cascading rollback
  • Lost update problems

7.1.7. Rigorous 2PL

Rule: All locks (both S and X) must be held until commit.

  1. Properties
    • Ensures schedules execute in the order of their equivalent serial schedule
    • Like Strict 2PL, free from irrecoverability, cascading rollback, and lost update problems
    • Not free from deadlock or starvation

7.2. Timestamp Ordering Protocol

7.2.1. Philosophy: Optimistic vs Pessimistic

Approach Protocol Assumption
Pessimistic Locking Assumes serializability will be violated
    Prevents potentially violating actions
Optimistic Timestamping Assumes serializability will be maintained
    Only interferes if actual violation occurs

7.2.2. Timestamp Basics

  • Each transaction is assigned a timestamp
  • Earlier transactions get smaller numbers (and are considered "older")
  • Each data item has two timestamps:
    • RTS(A): Highest timestamp of successful read transactions (max timestamp)
    • WTS(A): Highest timestamp of successful write transactions (max timestamp)
  • Initially, both are 0

7.2.3. Basic Timestamp Ordering Protocol (BTSOP)

  1. Properties
    • Executes if and only if CSS
    • Equivalent serial schedule is consistent with CSS and timestamp ordering
    • Ensures all operations are consistent with serial ordering based on timestamps
    • If TS(T1) < TS(T2), only allows actions consistent with serial schedule T1; T2
    • Executes only CSS schedules
    • CSS must have conflict-equivalent serial schedule matching timestamp ascending order

7.2.4. Timestamp Ordering with Thomas Write Rule

Principle: A write is useless if no one reads it before it is overwritten. Skip such writes.

Properties:

  • Can execute some view serializable schedules
  • More general than BTSOP

8. Summary of Protocol Characteristics

8.1. Comparison Table

Protocol Irrecoverable Cascading Rollback Lost Update Deadlock Starvation
Basic 2PL Yes Yes Yes Yes Yes
Strict 2PL No No No Yes Yes
Rigorous 2PL No No No Yes Yes
Conservative 2PL Yes Yes Yes No Yes

8.2. Detailed Characteristics

8.2.1. Basic 2PL

Suffers from:

  • Irrecoverability
  • Deadlock
  • Starvation
  • Cascading rollback (if recoverable)

8.2.2. Strict 2PL

Suffers from:

  • Deadlock
  • Starvation

Free from:

  • Irrecoverability
  • Cascading rollback
  • Lost update

8.2.3. Rigorous 2PL

Suffers from:

  • Deadlock
  • Starvation

Free from:

  • Irrecoverability
  • Cascading rollback
  • Lost update

Note: Rigorous 2PL is easier to implement because both lock types must be unlocked by committing.

8.2.4. Conservative 2PL

Suffers from:

  • Irrecoverability
  • Cascading rollback
  • Lost update problem
  • Starvation

Free from:

  • Deadlock

9. Key Takeaways

  1. ACID Properties are fundamental to correct transaction processing
  2. Serializability ensures isolation while allowing concurrency
  3. Recoverability ensures atomicity even when transactions abort
  4. Different locking protocols offer different trade-offs between safety and performance
  5. Timestamp ordering provides an optimistic alternative to locking
  6. Choose protocols based on your application's needs for recoverability, serializability, and performance
