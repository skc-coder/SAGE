* Introduction

This document covers the execution of transactions without conflicts and with concurrency for maximum speed.

A transaction consists of:
1. Reading data
2. Performing calculations
3. Writing back results

*Note:* The calculations themselves are not the database's concern.

* Write Operations

| Type          | Description                                    |
|---------------+------------------------------------------------|
| Normal Write  | A read operation has been performed before it  |
| Blind Write   | No read performed before it (e.g., overwriting)|

* ACID Properties

A correct set of transactions follows the ACID properties:

** Atomicity

- Transactions must either fully execute or have no effect
- Requires recovery mechanisms

** Consistency

- Transactions must start from a consistent state and commit with a consistent state
- What constitutes "consistent" is defined by business rules
- Affected by both recovery and concurrency control:
  - Poor recovery from abortions can cause inconsistency
  - Poor concurrency management can cause inconsistency

** Isolation

- Ensures that the effect of transactions is equivalent to running them serially, even when
  executed concurrently
- Ensured by maintaining serializability/concurrency control

** Durability
- Committed transaction effects must persist under all conditions
- Can be ensured by making data backups
- It comes into play after trasnacation has commited (atomicity)

* Schedule Requirements

We want schedules to be:
- Serializable
- Recoverable (specifically, cascadeless recoverable)
  
* Recovery
** Overview
- Atomicity requires a recovery management component
- Recovery systems use: undo, redo, rollback (to a state), aborting, and committing operations
- Requires transaction logs
- Atomicity depends on recoverability

*Important:* Recovery here refers to recovering from the effects of an aborted transaction,
not "Durability" recovery. "Durability" recovery focuses on recovring effect of commited trasnactions,
here we focus on getting trasnaction commited. Of course that recovery also shares some common goals.

** Recoverability Conflicts

A recoverable schdeule does NOT have WR (Write-Read) conflicts:
T1 writes T2 reads it and then T2 commits before T1

It may have WW (Write-Write) conflicts (also called lost update):
T1 writes T2 overwrites it and then T2 commits
https://stackoverflow.com/questions/855105/lost-update-in-concurrency-control

If WR is present then schedule is irrecoverable.

If NOT WR then solution is recoverable with cascading aborting/rollback of dependent
transactions.

*Note:* WW conflict doesn't affect recoverability; it may affect consistency, serializibility,
isolation but not recoveribilty.

** Types of Recoverable Schedules

*** Cascading Recoverable Schedules

*Condition:* If transaction T2 reads data written by transaction T1, then T1 must
commit before T2 ie. no WR conflict.

- If this condition is not satisfied, irrecoverability occurs
- When satisfied, we have a cascading recoverable schedule
- Removes the WR conflict
- However, cascading recovery can be costly (multiple transactions may need to abort)

*** Strict Recoverable Schedules

*Conditions:* Other transactions cannot read or write data that the current transaction
has written to (i.e., no WR or WW conflicts). (Why include WW tough?)

*Reasoning:*
- Removing  WW conflict cases, the DBMS doesn't have to  determine whether to keep the
  change or not saving time (?)
- When these conditions are met, we have a strict recoverable schedule

| Schedule Type              | Conflicts Allowed | Recovery Cost |
|----------------------------+-------------------+---------------|
| Cascading Recoverable      | WW only           | High          |
| Strict Recoverable         | None (no WR, WW)  | Low           |

* Serializability
** View Serializable (VSS)

The more general type of serializable schedule.

Two schedules S1 and S2 are view-equivalent when:

1. If transaction Tᵢ in S1 reads an initial value for object X, so does the same transaction
   Tᵢ in S2 (first read same)
2. If transaction Tᵢ reads a value (for object X) written by transaction Tⱼ in S1, it must do
   so in S2 (WR same)
3. If transaction Tᵢ in S1 performs the final write for object X, so does the same transaction
    Tᵢ in S2 (final write same)

** Conflict Serializable (CSS)

A more restrictive type of serializable schedule.

- When non-conflicting operations can be swapped (commuted) to transform one schedule
  into another, they are conflict-equivalent
- If a schedule is conflict-equivalent to a serial schedule, it is CSS
- Called "conflict equivalent" because the two schedules have the same conflicts
- Easier to implement than VSS

*Note:* Here "conflicts" don't depend on "commit" as they do in recoverability.

| Property                    | View Serializable | Conflict Serializable |
|-----------------------------+-------------------+-----------------------|
| Generality                  | More general      | More restrictive      |
| WW conflicts considered     | Can be ignored    | Must be considered    |
| Implementation complexity   | Harder            | Easier                |

** Precedence Graphs

Schedules can be depicted using precedence graphs, where arrows show which transaction
must come before another.

The arrow-making process differs based on serializability type:

- *CSS:* Arrows formed by WW, WR, RW conflicts
- *VSS:* Arrows formed by WR, RW conflicts (WW can be ignored, along with who
  did the last write)

*Note:* To be safe, also include the first condition from the view serializability definition.
We dont care about commit here. We just focus on same read and same final write.

** Schedule Types

#+BEGIN_SRC
Schedules
├── Serial (low throughput)
└── Concurrent (high throughput)
    ├── Serializable (equivalent to serial)
    └── Non-serializable
#+END_SRC

The DBMS deals with concurrent serializable schedules.

** Definition

- A schedule is equivalent to another if all reads are same and final writes are same:
  - Each read operation in both schedules reads the same value
  - The final write is performed by the same operation in both schedules
- A serializable concurrent schedules is one that is "equivalent" to serial schedules
- A serial schedule has the form: T₁ → T₂ → T₃

** Concurrency Control

- The concurrency control component prevents non-serializable schedules from running
  i.e. those which violate isolation and consistency condition
- Implemented using locks and other techniques
- Ensures only serial-equivalent schedules execute

** Possible Conflicts in Concurrent Schedules

*Note:* These are written in the order the conflict occurs (RW means read then write, so
RW != RAW, in fact opposite).

In all cases below, the first operation happens, then the second, but the transaction
of the first operation is uncommitted or still ongoing.

| Conflict | Name               | Description                                    |
|----------+--------------------+------------------------------------------------|
| RWR      | Unrepeatable Read  | Read, then Write, then Read again              |
| WR       | Dirty Read         | Write, then Read                               |
| WW       | Lost Update        | Write, then Write                              |

*** Important Notes About Conflicts

- These conflicts are NOT present in any serial schedule (each transaction commits
  before another starts)
- These MAY be present in a serializable schedule
- A conflict-equivalent schedule may have these conflicts, but a conflict-serializable
  schedule doesn't (by definition, it can be transformed into a serial one by commuting
  non-conflicting operations)
- These 'conflicts' may not actually be problems—they indicate ways transactions can
  affect each other and deviate from serial behavior.

*** Examples

*Example 1 (WR Conflict):*
If T1 writes to A and T2 reads A, this may not be problematic if in the serial schedule
T1 → T2, the same operation in T2 reads the same value written by T1.

The concerning thing is if: T2 read before T1 commited and T2 commits and T1 aborts.

*Example 2 (WW Conflict):*
If three transactions consist of only the operation W(B) and the schedule is equivalent
to T1→T2→T3, then the WW conflict between T1 and T2 is not significant as either can write
early or late. What matters is that the last update is done by T3.

This is the basis of "view serializability"—the view must be the same.

In conflict serializability: W₁(B) → W₂(B) → W₃(B) is not equivalent to W₂(B) → W₁(B) → W₃(B).
In view serializability they are equivalent.

** Types of Serializable Schedules
* Concurrency Control Protocols
Serializibility is implemented using these mechanisms:
** LOCK BASED PROTOCOL
*** Lock Types

| Lock Type         | Symbol | Allows Reading | Allows Writing | Can Share |
|-------------------+--------+----------------+----------------+-----------|
| Shared Lock       | S      | Yes            | No             | Yes       |
| Exclusive Lock    | X      | Yes            | Yes            | No        |

*** Basic 2PL

    Ensures serializability by preventing non-serializable schedules.
    If a schedule follows 2PL, it is Conflict Serializable.
    The conflict equivalent serial schedule is determined by the order of Lock Points.
    Note: Every conflict serializable schedule is NOT necessarily allowed by 2PL.
*** Lock Point
    Defined as the point where the growing phase ends (last lock acquire).
    It is the moment a transaction acquires its final required lock.
    Example: If T1​ acquires its last lock before T2​, the serial order is T1​→T2​.
    Variants of 2PL
*** 2PL with lock upgrading/downgrading
    Lock Conversion (Upgrading/Downgrading)

    Upgrading: Converting a Shared (S) lock to an Exclusive (X) lock. Allowed only during the Growing Phase.

    Downgrading: Converting an Exclusive (X) lock to a Shared (S) lock. Occurs in the Shrinking Phase.

    Rules:

        Cannot upgrade if already in the shrinking phase.

        Downgrading immediately triggers the start of the shrinking phase.

    Impact: Allows for some extra conflict serializable schedules compared to basic 2PL without conversion.
*** Strict 2PL
    Constraint: All Exclusive (X) locks held by a transaction must be released only after the Commit operation.
    Shared (S) locks can be released at any point after use.
    Benefits: Free from Irrecoverability (X lock realsed after commit, so it satisfies no read or no write, hence strict recoverable),
    Cascading Rollbacks, and Lost-update problems.
    Limitations: Not free from Deadlock or Starvation.

*** Conservative 2PL
    Purpose: Specifically designed to solve the problem of Deadlock.
    Mechanism: Dis-satisfies the "Hold & Wait" condition by using "Hold or Wait".
    Protocol:
        Transaction must request all required locks before starting execution.
        Execution begins only if ALL locks are granted.
        If any lock is unavailable, it releases all currently held locks and enters a "time out" period before retrying.
    Drawbacks:
        May suffer from Irrecoverability and Cascading Rollbacks.
        Potential for Starvation increases.
*** Rigorous 2PL

    Constraint: Both Shared (S) and Exclusive (X) locks must be held until the transaction Commits.
    Implementation: Easier to implement than Strict 2PL as all locks are simply released after commit.
    Benefits: Free from Irrecoverability, Cascading Rollback, and Lost-update problems.
    Limitations: Still susceptible to Deadlock and Starvation.
** Timestamp Ordering Protocol

*** Philosophy: Optimistic vs Pessimistic

| Approach     | Protocol        | Assumption                                              |
|--------------+-----------------+---------------------------------------------------------|
| Pessimistic  | Locking         | Assumes serializability will be violated                |
|              |                 | Prevents potentially violating actions                  |
| Optimistic   | Timestamping    | Assumes serializability will be maintained              |
|              |                 | Only interferes if actual violation occurs              |

*** Overview

Timestamp ordering protocols are concurrency control mechanisms that use transaction timestamps to determine the
serializability order of conflicting operations in database systems.
*** Transaction Timestamps
- Each transaction is assigned a unique timestamp when it begins
- Earlier transactions receive smaller timestamp values (considered "older")
- *Important:* Transaction timestamps NEVER CHANGE during execution

*** Data Item Timestamps
Each data item maintains two timestamps that MAY CHANGE during execution:

- *RTS(A):* Read Timestamp - Highest timestamp among all transactions that have successfully read item A
- *WTS(A):* Write Timestamp - Highest timestamp among all transactions that have successfully written item A
- *Initial Values:* Both RTS(A) and WTS(A) are initialized to 0

*** Basic Timestamp Ordering Protocol (BTSOP)

**** Fundamental Principle
The Basic Timestamp Ordering Protocol ensures that transactions execute in a manner consistent with their timestamp order,
producing only conflict serializable schedules.

**** Key Properties
- Executes if and only if the schedule is Conflict Serializable (CSR)
- The equivalent serial schedule must match the timestamp ordering
- If TS(T₁) < TS(T₂), only allows actions consistent with serial schedule T₁; T₂
- Guarantees conflict serializability by enforcing timestamp-based ordering

**** Serializability Guarantee
- *Allows:* Only Conflict Serializable (CSR) schedules
- *Requirement:* The conflict-equivalent serial schedule must follow ascending timestamp order
- *Rejection:* Schedules that are CSR but whose serial order differs from timestamp order

**** Protocol Rules

***** Read Operation: Rᵢ(A)
Transaction Tᵢ requests to read data item A:

1. *If TS(Tᵢ) < WTS(A):*
   - Transaction Tᵢ is reading a value already overwritten by a younger transaction
   - *Action:* REJECT and ABORT Tᵢ (violates timestamp order)

2. *If TS(Tᵢ) ≥ WTS(A):*
   - *Action:* ALLOW the read operation
   - Update: RTS(A) = max(RTS(A), TS(Tᵢ))

***** Write Operation: Wᵢ(A)
Transaction Tᵢ requests to write data item A:

1. *If TS(Tᵢ) < RTS(A):*
   - A younger transaction has already read a later value
   - *Action:* REJECT and ABORT Tᵢ (violates timestamp order)

2. *If TS(Tᵢ) < WTS(A):*
   - A younger transaction has already written a later value
   - *Action:* REJECT and ABORT Tᵢ (violates timestamp order)

3. *If TS(Tᵢ) ≥ max(RTS(A), WTS(A)):*
   - *Action:* ALLOW the write operation
   - Update: WTS(A) = TS(Tᵢ)

*** Timestamp Ordering with Thomas Write Rule (TWR)

**** Core Principle
#+BEGIN_QUOTE
A write operation is useless if no transaction reads it before it is overwritten by another transaction.
Therefore, such obsolete writes can be safely ignored.
#+END_QUOTE

**** Enhanced Protocol Rules

**** Read Operation: Rᵢ(A)
Same as BTSOP (no changes)

**** Write Operation: Wᵢ(A) - WITH Thomas Write Rule
Transaction Tᵢ requests to write data item A:

1. *If TS(Tᵢ) < RTS(A):*
   - A younger transaction has already read a later value
   - *Action:* REJECT and ABORT Tᵢ

2. *If RTS(A) ≤ TS(Tᵢ) < WTS(A):*
   - A younger transaction has already overwritten this value
   - *Thomas Write Rule:* IGNORE the write (don't abort)
   - Rationale: This write would be immediately overwritten anyway

3. *If TS(Tᵢ) ≥ WTS(A):*
   - *Action:* ALLOW the write operation
   - Update: WTS(A) = TS(Tᵢ)

*** Key Advantages
- Can execute some View Serializable (VSR) schedules that are NOT Conflict Serializable
- More permissive than BTSOP by ignoring obsolete writes
- Handles write-write conflicts more gracefully (blind writes)
- Reduces unnecessary transaction aborts

*** Comparison: BTSOP vs Thomas Write Rule

**** Serializability Hierarchy

#+BEGIN_EXAMPLE
                View Serializable (VSR)
                        |
                        |
           +------------+------------+
           |                         |
    Conflict Serializable (CSR)      |
           |                         |
           |                         |
        BTSOP ⊂ Thomas Write Rule ⊂ VSR
#+END_EXAMPLE

**** Formal Relationships
- BTSOP ⊂ Thomas Write Rule (TWR is strictly more general)
- BTSOP ⟹ Conflict Serializable (CSR)
- Thomas Write Rule ⟹ View Serializable (VSR)
- Every schedule allowed by BTSOP is also allowed by TWR
- TWR allows additional VSR schedules through blind write optimization

**** Feature Comparison

| Feature                    | BTSOP                        | Thomas Write Rule              |
|----------------------------+------------------------------+--------------------------------|
| Serializability Type       | Conflict Serializable (CSR)  | View Serializable (VSR)        |
| Write-Write Conflicts      | Always aborts older writes   | Ignores obsolete writes        |
| Read Rules                 | Same as TWR                  | Same as BTSOP                  |
| Abort Rate                 | Higher                       | Lower                          |
| Complexity                 | Simpler                      | Slightly more complex          |
| Schedule Permissiveness    | More restrictive             | More permissive                |

- No deadlocks (transactions never wait for locks)
- May cause irrecoveribilty and all other problems

* Key Takeaways

1. *ACID Properties* are fundamental to correct transaction processing
2. *Serializability* ensures isolation while allowing concurrency
3. *Recoverability* ensures atomicity even when transactions abort
4. Different *locking protocols* offer different trade-offs between safety and performance
5. *Timestamp ordering* provides an optimistic alternative to locking
6. Choose protocols based on your application's needs for recoverability, serializability, and performance
